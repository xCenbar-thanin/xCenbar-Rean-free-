មេរៀន ១Security Mindset & Threat Modeling (STRIDE)

មុនសរសេរកូដ សួរ ៤ សំណួរ៖ យើងកំពុងសាងសង់អ្វី? អ្វីអាចខុស? យើងនឹងធ្វើអ្វី? យើងធ្វើបានល្អឬទេ?

STRIDEការគំរាមកំហែងការពារ
Spoofingក្លែងខ្លួនជាអ្នកផ្សេងAuthentication, MFA
Tamperingកែទិន្នន័យ (តម្លៃក្នុង Cart)Validation ខាង Server, Integrity
Repudiationបដិសេធថាមិនបានធ្វើAudit logs
Information disclosureលេចធ្លាយទិន្នន័យEncryption, Access control
Denial of serviceធ្វើឱ្យសេវាគាំងRate limit, Timeouts, CDN
Elevation of privilegeStaff ក្លាយជា AdminAuthorization ខាង Server
⚠️ ច្បាប់មាស៖ កុំទុកចិត្ត Client។ អ្វីៗពី Browser (Form, Query, Header, Cookie, តម្លៃក្នុង Hidden field, JavaScript validation) អាចត្រូវបានកែ។ Validation និង Authorization ត្រូវធ្វើ ខាង Server ជានិច្ច។

✍️ លំហាត់ ១

ធ្វើ STRIDE សង្ខេបលើមុខងារ «Checkout» របស់ហាងអនឡាញ (Client ផ្ញើ { items:[{id, qty, price}], total })។ រកការគំរាមកំហែង ៣។

មើលចម្លើយ
  1. Tampering៖ កែ price/total ជា 0.01 → Server ត្រូវ មិនទទួល price ពី Client; យកតម្លៃពី Database ហើយគណនា total ខាង Server
  2. Tampering៖ qty: -5 → Validation (integer ≥ 1, ≤ ស្តុក)
  3. Elevation / IDOR៖ ប្រើ Coupon/Address របស់អ្នកផ្សេង → ពិនិត្យ Ownership
  4. DoS៖ Checkout ១០០០ ដង/នាទី → Rate limit + Idempotency key

មេរៀន ២HTTPS, TLS & HSTS

  • HTTPS = HTTP + TLS៖ Encrypt ទិន្នន័យ (Password, Cookie) និងផ្ទៀងផ្ទាត់ថាជា Server ពិត (Certificate)
  • Certificate ឥតគិតថ្លៃ៖ Let's Encrypt (Certbot) · Vercel/Netlify/Cloudflare ផ្តល់ដោយស្វ័យប្រវត្តិ
  • ប្រើ TLS 1.2+ (ល្អបំផុត TLS 1.3) · បិទ SSLv3, TLS 1.0/1.1
  • HSTS៖ ប្រាប់ Browser ឱ្យប្រើ HTTPS ជានិច្ច (ការពារ SSL stripping)
  • Redirect HTTP → HTTPS (301) · គ្មាន Mixed content (រូប/Script តាម http:// លើទំព័រ https://)

✍️ លំហាត់ ២

ហេតុអ្វីគ្រាន់តែ Redirect HTTP → HTTPS មិនទាន់គ្រប់គ្រាន់ ហើយត្រូវការ HSTS?

មើលចម្លើយ

Request ដំបូង (វាយ kafe.com ឬ Link http://) នៅតែទៅតាម HTTP មុនពេល Redirect — អ្នកនៅលើបណ្តាញដដែល (Wi-Fi សាធារណៈ) អាចស្ទាក់វាបាន។ HSTS ធ្វើឱ្យ Browser ប្តូរទៅ HTTPS ដោយខ្លួនឯងមុនផ្ញើ រយៈពេល max-age · preload ដាក់ Domain ក្នុងបញ្ជីរបស់ Browser សូម្បីការចូលលើកដំបូង។

មើលចម្លើយ

frame-src = Site របស់អ្នកដាក់អ្នកណាក្នុង iframe បាន · frame-ancestors = អ្នកណាអាចដាក់ Site របស់អ្នក ក្នុង iframe។

មេរៀន ៥Cross-Site Scripting (XSS)

XSS = Attacker ធ្វើឱ្យ JavaScript របស់គេរត់ក្នុង Website របស់អ្នក ក្នុង Browser របស់អ្នកប្រើផ្សេង → លួច Token, ធ្វើសកម្មភាពជំនួស, កែទំព័រ។ ប្រភេទ៖ Stored (រក្សាក្នុង DB — Comment), Reflected (ពី URL), DOM-based (JavaScript ខាង Client)។

ការពារ XSS

  1. Output encoding៖ ប្រើ textContent · Template engine/React escape ដោយស្វ័យប្រវត្តិ ({comment})
  2. ជៀសវាង innerHTML, document.write, eval, dangerouslySetInnerHTML
  3. បើត្រូវបង្ហាញ HTML (Rich text) → Sanitize ដោយ DOMPurify
  4. ពិនិត្យ URL៖ ទទួលតែ https: (ការពារ javascript: ក្នុង href)
  5. CSP ជាស្រទាប់ទី ២ · Cookie HttpOnly ដើម្បីកុំឱ្យ JS អានបាន

✍️ លំហាត់ ៥

ទំព័រស្វែងរកបង្ហាញ resultTitle.innerHTML = "លទ្ធផលសម្រាប់: " + new URLSearchParams(location.search).get("q")។ ប្រភេទ XSS អ្វី? កែយ៉ាងដូចម្តេច?

មេរៀន ៦Cookies, Sessions, CSRF & CORS

CSRF (Cross-Site Request Forgery)៖ Site អាក្រក់ធ្វើឱ្យ Browser របស់អ្នក (ដែល Login រួច) ផ្ញើ Request ទៅ Site ពិត ជាមួយ Cookie ដោយស្វ័យប្រវត្តិ (ឧ. ផ្ទេរប្រាក់)។

  • SameSite=Lax/Strict Cookie (Default របស់ Browser ទំនើបគឺ Lax)
  • កុំប្រើ GET សម្រាប់សកម្មភាពដែលប្តូរទិន្នន័យ
  • CSRF token ក្នុង Form (Synchronizer token) ឬ ពិនិត្យ Origin/Sec-Fetch-Site header
  • API ដែលប្រើ Authorization: Bearer header (មិនមែន Cookie) មិនរងគ្រោះ CSRF ប៉ុន្តែ Token ត្រូវការពារពី XSS

✍️ លំហាត់ ៦

Bank App មាន GET /transfer?to=123&amount=100 ហើយប្រើ Cookie Session។ ពន្យល់ហានិភ័យ និងដំណោះស្រាយ ៣។

មើលចម្លើយ

Attacker ដាក់ <img src="https://bank.com/transfer?to=666&amount=100"> លើ Site របស់គេ → Browser ផ្ញើ Cookie ជាមួយ (CSRF) — GET ក៏ងាយត្រូវ Cache/Log/Prefetch។

  1. ប្តូរជា POST + Body
  2. Cookie SameSite=Strict (ឬ Lax) + HttpOnly + Secure
  3. CSRF token + ពិនិត្យ Origin · បញ្ជាក់ម្តងទៀត (OTP/MFA) សម្រាប់ប្រតិបត្តិការធំ

✍️ លំហាត់ ៧

ហេតុអ្វី SHA-256(password) មិនសមស្រប សូម្បីតែវាជា Hash ខ្លាំង? ហើយ Salt ជួយអ្វី?

មើលចម្លើយ

SHA-256 លឿនពេក៖ GPU អាចសាកពាន់លានដង/វិនាទី → Brute-force Password ខ្លីៗបានលឿន។ bcrypt/Argon2 យឺតដោយចេតនា (Cost factor) ហើយ Argon2 ប្រើ Memory ច្រើន។ Salt (Random ផ្សេងគ្នាសម្រាប់ User នីមួយៗ) ធ្វើឱ្យ Password ដូចគ្នាមាន Hash ខុសគ្នា → មិនអាចប្រើតារាងគណនាទុកមុន (Rainbow table) ហើយ Attacker ត្រូវ Crack ម្នាក់ៗ។

  • ការលាក់ប៊ូតុងក្នុង React មិនមែនជាការការពារ — API ត្រូវពិនិត្យជានិច្ច
  • ID ងាយទាយ (1, 2, 3) មិនមែនជាបញ្ហាដើម — បញ្ហាគឺ គ្មានការពិនិត្យសិទ្ធិ (UUID ជួយបន្ថែមប៉ុណ្ណោះ)

មេរៀន ១១File Upload & SSRF

SSRF (Server-Side Request Forgery)៖ Server ទៅទាញ URL ដែល User ផ្តល់ (ឧ. «បញ្ចូលរូបពី URL») → Attacker ផ្តល់ URL ខាងក្នុង (http://localhost:…, http://169.254.169.254/ Cloud metadata) ដើម្បីចូលប្រព័ន្ធខាងក្នុង។

✍️ លំហាត់ ១១

User Upload File ឈ្មោះ ../../server.js ហើយ App រក្សាទុក path.join("uploads", file.originalname)។ បញ្ហាអ្វី? កែយ៉ាងដូចម្តេច?

មើលចម្លើយ

Path traversal — ../ ចេញក្រៅ Folder uploads ហើយអាចសរសេរជាន់ File កូដ។ កែ៖ កុំប្រើឈ្មោះពី User — បង្កើត randomUUID() + Extension ពី Allowlist, រក្សាទុកក្រៅ Web root ឬក្នុង Object storage ហើយ Server/Folder upload គ្មានសិទ្ធិ Execute។

  2. localStorage៖ XSS ណាមួយអាចអាន Token → ប្រើ HttpOnly Secure SameSite Cookie, CSP, exp ខ្លី

Incident Response (ពេលមានហេតុការណ៍)

  1. Contain — បិទ Feature/Account, Revoke Keys, Block IP
  2. Investigate — Logs: ពេលណា? ទិន្នន័យអ្វី? ប៉ុន្មាននាក់?
  3. Fix — ជួសជុល + Test + Deploy
  4. Notify — អ្នកប្រើ/អាជ្ញាធរ តាមច្បាប់
  5. Learn — Post-mortem ដោយមិនបន្ទោស ហើយបន្ថែម Test/Alert
